# ZeroJ Jubjub-EdDSA v1 — Normative Specification

**Suite identifier:** `ZeroJ-JubjubEdDSA-v1`
**Status:** Normative. Required by ADR-0037 Decision 5 as a prerequisite for any
domain-separation code.
**Date:** 2026-07-25

This document pins every value and encoding a second implementation would need in order to
interoperate. Where ADR-0037 states *what* must be fixed, this states *the actual values*.
Anything not written here is not part of the suite.

Changing any constant, tag, encoding, or arity in this document produces a different scheme.
Signatures and credentials issued under a previous revision do not verify under a new one.
Such a change requires a new suite identifier (`-v2`), not an edit to this file.

## 2. Poseidon parameters

Two presets are used. Both are generated by the pinned hadeshash reference script
(commit `208b5a164c6a252b137997694d90931b2bb851c5`) and reproduced byte-for-byte by ZeroJ's
Grain LFSR port.

| Preset | `t` | `α` | `RF` | `RP` | Rate | Used for |
|---|---:|---:|---:|---:|---:|---|
| `PoseidonParamsBLS12_381T3` | 3 | 5 | 8 | 57 | 2 | nonce derivation |
| `PoseidonParamsBLS12_381T6` | 6 | 5 | 8 | 60 | 5 | challenge |

Generation commands:

```
sage generate_parameters_grain.sage 1 0 255 3 8 57 0x73eda753...00000001
sage generate_parameters_grain.sage 1 0 255 6 8 60 0x73eda753...00000001
```

The `t=6` run reports `Algorithm 1: [True, 0]`, `Algorithm 2: [True, None]`,
`Algorithm 3: [True, None]` — first-pass acceptance of the Cauchy MDS matrix, which is the
precondition for ZeroJ's Java port omitting those algorithms. This is pinned by
`PoseidonParamsT6SageConformanceTest`, including a SHA-256 digest over all 444 parameter
values:

```
SHA-256( C[0..407] || M[0..35] ), each value as 32-byte big-endian
  = b8791aa751cb4b2d7fad4767f14561aff24c08a56ce52828ec3f8f6cd436a34f
```

### 2.1 Sponge convention

For a width-`t` permutation, ZeroJ's convention is:

- `state[0]` is the **capacity** cell,
- `state[1 .. t-1]` are **rate** cells, filled with inputs in order and zero-padded,
- the output is `state[0]` after one permutation.

Domain separation is applied by seeding the capacity cell with a tag rather than zero. This
costs nothing: it replaces a constant that was already there.

## 3. Domain-separation tags

Each tag is a field element derived from its ASCII label:

```
tag(label) = OS2IP( SHA-512(label) ) mod p         // SHA-512 output read big-endian
```

The derivation is documented so it can be audited, but implementations MUST use the pinned
literals below rather than re-deriving at runtime.

| Use | Label | Tag |
|---|---|---|
| Challenge | `ZeroJ-JubjubEdDSA-v1-challenge` | `0x00eddbdea8f7a5571d7ba19cab887f55f5225616ae1a827da58198fec59f999b` |
| Nonce | `ZeroJ-JubjubEdDSA-v1-nonce` | `0x6737a0f0a6c1453e3776d8f7f0ab0181b254d79b0d450d72c46803ed651ae865` |

## 4. `hashToField(msg)` — byte strings to field elements

Maps an arbitrary byte string to an element of `[0, p)`.

```
DST  = "ZeroJ-JubjubEdDSA-v1-hashToField"            // 32 ASCII bytes
wide = SHA-512( len(DST) as 1 byte
              || DST
              || len(msg)  as 8 bytes, big-endian, unsigned
              || msg )
out  = OS2IP(wide) mod p                              // wide read big-endian, 64 bytes
```

Notes, all normative:

- The DST and the message are **both length-prefixed**, so no two distinct `(DST, msg)` pairs
  share a preimage and callers cannot create ambiguity by concatenation.
- `len(msg)` is an unsigned 64-bit big-endian count of bytes.
- 512 bits reduced into a 255-bit field leaves a modular bias of about `2^-257`. A bare
  32-byte digest would have left a bias near `2^-1` for the low residues and MUST NOT be used.
- SHA-512, not Poseidon: the input is a byte string of arbitrary length, and a byte-oriented
  hash avoids inventing a sponge padding rule for it.

## 5. Keys

```
sk  ∈ [1, l)          sampled uniformly, by rejection sampling — never `random mod l`
pk  = [sk]·G
```

A verifier MUST reject `pk = O` (the identity) and MUST establish that `pk` lies in the
prime-order subgroup, either by checking `[l]·pk == O` or by binding `pk` to a registry entry
whose membership was checked at registration. See §8.

---

## 6. Nonce and challenge

```
nonce:      r = Poseidon_t3( capacity = NONCE_TAG,     rate = (sk, msg) ) mod l
challenge:  k = Poseidon_t6( capacity = CHALLENGE_TAG, rate = (R.u, R.v, pk.u, pk.v, msg) ) mod l
```

- All point coordinates are **affine** and canonical in `[0, p)`. A projective representative
  MUST be normalised before hashing; hashing `(U, V)` of a non-normalised point is a different
  value for the same point and is a Fiat–Shamir grinding vector.
- `msg ∈ [0, p)`. Values outside that range are rejected, not reduced: reduction would make a
  signature over `msg` also valid for `msg + p`.
- The challenge absorbs five elements, which is why it needs rate ≥ 5 and therefore `t = 6`.
  `t = 5` has rate 4 and cannot express this construction.
- `pk` is included in the challenge to defeat key substitution.

---

## 7. Sign and verify

**Sign(sk, msg) → (R, S)**

```
1.  require 0 < sk < l  and  0 <= msg < p
2.  r = nonce(sk, msg)
3.  R = [r]·G
4.  k = challenge(R, pk, msg)
5.  S = (r + k·sk) mod l
```

**Verify(pk, msg, R, S) → bool**

```
1.  require 0 <= msg < p                       (caller error otherwise, not a bad signature)
2.  reject if pk == O
3.  reject if pk ∉ prime-order subgroup        (see §8 for the in-circuit variants)
4.  reject if R  ∉ prime-order subgroup
5.  reject if S ∉ [0, l)                       (rejects the S + l alias)
6.  k = challenge(R, pk, msg)
7.  accept iff [S]·G == R + [k]·pk
```

Verification is **cofactorless**. Step 7 is checked as written, not as `[8]·(...)`.

Rationale, from ADR-0037 Decision 4: cofactoring makes every point of order dividing 8 —
including the identity — a universal forgery, because `[8]·([k]·pk) = O` collapses the
equation to `[8S]·G == [8]·R`. Cofactorless verification also forces the accepted `R` into the
prime-order subgroup algebraically, since the other two terms lie there.

This gives canonical *acceptance semantics*, not uniqueness of `R`: a signer who deviates from
the deterministic nonce can produce a different, entirely valid signature over the same
`(pk, msg)`. A protocol using `R` as a uniqueness key therefore still depends on deterministic,
single issuance, and SHOULD prefer a nullifier derived from a credential identifier.

## 8. In-circuit verification

The relation is identical to §7 step 7, with these additional constraints, and with the `pk`
trust assumption made explicit in the entry-point name.

**Point binding.** Every prover-supplied point enters as affine `(u, v)` wires and is bound
with: `Z := 1`, `T := u·v`, and the affine curve equation `v² − u² == 1 + d·u²·v²`. Raw
extended-coordinate input is not accepted — unconstrained `Z`/`T` wires are solvable against
the verification equation and yield a forgery for a never-signed message.

**Challenge reduction.** The circuit witnesses `(kQuotient, kModL)` and asserts
`kRaw == kQuotient·l + kModL` over the field, plus all three of:

```
kQuotient <= 8
kModL     <  l
kQuotient == 8  ⇒  kModL < δ
```

Together these force `kQuotient·l + kModL < p`, so the field equation cannot wrap and the
decomposition is unique. They are also complete: every `kRaw ∈ [0, p)` has a witness. Omitting
the third conjunct admits `(q + 8, kModL + δ)` as a second challenge for one transcript.

**Public-key handling.** Both entry points assert `[8]·pk != O`, which rejects the identity and
every point of order dividing 8. They differ in how subgroup membership is established:

| Entry point | `pk` requirement | Cost of the check |
|---|---|---|
| `verifyStrict` | in-circuit `[l]·pk == O` | ~8.5k constraints |
| `verifyWithRegisteredKey` | `pk` must be a public input or a circuit constant, enforced by the DSL against circuit-owned wire IDs | negligible |

`verifyWithRegisteredKey` shifts an obligation onto the protocol rather than removing it: the
final verifier MUST bind that public value to a registry entry whose subgroup membership was
checked off-circuit at registration. Being verifier-visible is not the same as being a valid
key. A mixed-order `pk = pk' + T` passes `[8]·pk != O` and is accepted by
`verifyWithRegisteredKey`; only `verifyStrict` rejects it.

---

## 9. Point encoding

32 bytes, Zcash/zkcrypto convention: little-endian `v` in the low 255 bits, with the top bit of
byte 31 set iff `u` is odd. Decoding MUST reject `v >= p` and MUST reject the non-canonical
encoding with `u = 0` and the sign bit set. Decoding does not check subgroup membership;
callers handling untrusted input MUST do so separately.

---

## 10. Non-goals

- **Not interoperable with RFC 8032 / Ed25519 / Sapling-EdDSA.** The challenge and nonce use
  Poseidon so the verification equation is cheap inside a BLS12-381 SNARK.
- **Signing is not constant-time.** `sign` performs secret-dependent scalar multiplication over
  variable-time `BigInteger` and feeds `sk` through Poseidon's variable-time field arithmetic.
  Per ADR-0037 Decision 8 this signer is not approved for value-bearing issuance on shared or
  network-reachable infrastructure. Verification handles only public data.
- **Batch verification is not specified.** Any future batch verifier MUST reproduce the
  acceptance semantics of §7 exactly, including the cofactorless equation and the subgroup
  checks; a cofactored relaxation is not an equivalent optimisation.
