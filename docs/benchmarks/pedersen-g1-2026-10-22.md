# BLS12-381 G1 Pedersen (`pedersen-bls12-381-g1-v1`, `-bytes-v1`): host and on-chain measurements (ADR-0060)

**Date:** 2026-10-22

**Harnesses:**
- **Host:** `G1PedersenBenchmark`, a standalone `main` that launches three fresh JVM forks.
  Run it with `./gradlew :zeroj-bls12381:g1PedersenBenchmark`.
- **Julc VM:** `PedersenG1LibVmTest` and `PedersenG1BuiltinEvidenceTest` in `zeroj-onchain-julc`,
  and `G1PedersenOnChainTest` in `zeroj-integration-tests`.
- **DevKit:** `G1PedersenDevKitE2ETest` and `G1PedersenNodeEvidenceE2ETest`, run with
  `./gradlew :zeroj-integration-tests:e2eTest --tests '*G1Pedersen*'`.

**Machine:** Apple M4 Max (arm64, 16 cores), macOS 26.0.1, Oracle GraalVM JDK 25.0.2 (JIT, not
native image).

These numbers describe this JVM, this CPU and these cost models only. They are records, not
checks (ADR-0060 I11, `commitment-profiles-v1` §15). They make no timing-side-channel claim.

**Not measured:**
- GraalVM native image;
- x86-64;
- the blst provider in the host harness (the harness measures the pure-Java provider; see the
  reviewer measurement below).

## Host operations (pure-Java provider)

Each figure is the median, across 3 forks, of each fork's p50 and p95. Allocation is per
operation, on the calling thread.

| Operation | p50 | p95 | Allocated/op |
|---|---:|---:|---:|
| `commitScalar` (generation, secret path) | 15.50 ms | 16.08 ms | 9.8 MB |
| `decode` (strict, subgroup check) | 4.37 ms | 4.66 ms | 2.4 MB |
| `verifyScalar`, commitment already decoded (V1) | 17.38 ms | 17.89 ms | 9.5 MB |
| `decode` + `verifyScalar` of a received commitment (V1) | 21.47 ms | 21.95 ms | 11.9 MB |
| `withPublicDelta`, 64-bit delta (V3) | 0.44 ms | 0.49 ms | 265 KB |
| `add` (one V3 sum term) | 9.4 µs | 10.0 µs | 6.7 KB |
| Envelope encode + decode | 4.34 ms | 4.57 ms | 2.4 MB |
| `randomBlinding` | 2.2 µs | 4.4 µs | 808 B |
| Byte map, 0 B / 1 KiB / 1 MiB / 16 MiB | 8.5 µs / 4.6 µs / 0.40 ms / 6.45 ms | — | 1.6 KB (constant) |
| `commitBytes`, 0 B / 1 KiB / 1 MiB / 16 MiB | 14.9 / 14.9 / 15.2 / 21.3 ms | — | 9.7 MB |
| `verifyBytes`, 0 B / 1 KiB / 1 MiB / 16 MiB | 16.8 / 16.9 / 17.3 / 23.6 ms | — | 9.4–9.5 MB |

Every result is consumed through a volatile sink, so the JIT cannot drop the measured work.

The byte map allocates the same amount whatever the payload size (spec §5.2). The 0 B figure ran
first and includes JIT warm-up that the 1 KiB figure does not.

**Wall time per operation** across threads:

| Operation | 1 thread | 8 threads |
|---|---:|---:|
| `commitScalar` | 14.88 ms | 1.94 ms |
| `decode` + `verifyScalar` | 21.21 ms | 2.72 ms |

**Where verification time goes.** The pure-Java provider's `g1ScalarMul` and
`g1SecretScalarMul` re-validate their input point on every call, with `Bls12381Codecs.requireValid`.
That validation includes `G1Point.isInSubgroup`, an affine double-and-add `[q]P` that takes about
4.3 ms here. The bases are fixed and already validated, so roughly 10 ms of each verification and
each generation repeats work.
- A Jacobian `[q]P` measured about 0.6 ms in the same JVM.
- Both are shared primitives, used by Groth16, BBS and the providers, so ADR-0060 does not change
  them. This is recorded as a follow-up.
- Generation adds one more subgroup check, on the public sum of the two provider results (spec §8).
- **The blst provider is not faster here.** A review measurement in the same JVM (single process,
  not the harness) gave `commitScalar` 26.5 ms with blst against 19.0 ms pure Java (before the
  generation check was reduced to one subgroup check), and `verifyScalar` 17.2 ms against 16.9 ms.
  The blst provider validates its input point and decodes its output through the same pure-Java
  `requireValid`, so the affine subgroup checks dominate either way.
- No check in the profile was removed or weakened for speed.

## Cardano: Julc VM (Plutus V3, PV11 cost model)

Mainnet and DevKit limits per transaction (PV11): 10,000,000,000 steps, 16,500,000 memory units
and 16,384 octets.

| Operation (`PedersenG1Lib`, test probes) | CPU steps | % of step limit | Memory | % of memory limit |
|---|---:|---:|---:|---:|
| Strict decode of one commitment (length, `uncompress`, round trip) | 77,017,395 | 0.77% | 46,246 | 0.28% |
| Decode + V1 scalar opening (two `scalarMul`) | 342,762,943 | 3.43% | 83,534 | 0.51% |
| Same, with one two-term `multiScalarMul` | 555,858,608 | 5.56% | 60,286 | 0.37% |
| Decode + V3 public delta (`[|δ|]·G`, add, compare) | 227,832,351 | 2.28% | 125,908 | 0.76% |
| Two decodes + `add` + compare | 138,206,070 | 1.38% | 66,995 | 0.41% |
| `hashToGroup` reproduction of `G` and `H` | 129,111,063 | 1.29% | 45,557 | 0.28% |
| Decode + byte opening, 0 B | 346,306,758 | 3.46% | 81,867 | 0.50% |
| Decode + byte opening, 1 KiB | 349,318,094 | 3.49% | 82,506 | 0.50% |
| Decode + byte opening, 8 KiB | 370,399,182 | 3.70% | 86,986 | 0.53% |
| Decode + byte opening, 16 KiB | 394,491,854 | 3.94% | 92,106 | 0.56% |
| Decode + byte opening, 32 KiB | 442,677,198 | 4.43% | 102,346 | 0.62% |

The library decompresses its pinned bases only inside the operations that use them. Julc
evaluates zero-argument library methods once at script start, so an earlier version that exposed
the bases as zero-argument accessors made every linking script pay about 106M steps for two
`uncompress` calls it might not need; the figures above are for the lazy version.

**MSM against two `scalarMul`.** A two-term `multiScalarMul` costs about 213M more CPU steps than
two `scalarMul`, so the library uses two `scalarMul`. ADR-0060 D9 adopts the MSM only if it is
cheaper.

**Byte openings.** Each payload octet adds about 2,940 CPU steps, so CPU does not bind. Transaction
size does (see the payload limit below).

**An `n`-term sum.** A probe that decodes two commitments, adds them and compares the encoding
costs 138,206,070 steps; one strict decode costs 77,017,395. Each further term therefore costs
about 61M steps (one `uncompress`, the round-trip check and one `add`), and a sum of `n` received
commitments about `16M + 61M·n` steps under this cost model, the fixed part being the script's
own context and redeemer handling.

## Cardano: Yaci DevKit (protocol version 11)

**Parameters** (DevKit epoch 28):
- `min_fee_a` 44, `min_fee_b` 155,381
- `price_mem` 0.0577, `price_step` 0.0000721
- `min_fee_ref_script_cost_per_byte` 15
- `max_tx_size` 16,384, `max_tx_ex_mem` 16,500,000, `max_tx_ex_steps` 10,000,000,000

**Honest transactions.** Ex-units were computed by `JulcTransactionEvaluator` because DevKit's
`/evaluate` cannot initialise blst on aarch64 (ADR-0056). The node accepted each transaction.

| Flow | Tx size (wire) | Fee paid (lovelace) | Memory | Steps |
|---|---:|---:|---:|---:|
| Scalar opening | 1,907 | 278,159 | 147,275 | 359,607,887 |
| Running total `+250` | 2,912 | 322,436 | 255,735 | 273,594,722 |
| Running total `−100` | 2,876 | 320,830 | 255,153 | 273,763,193 |
| Byte opening, 300 B | 2,169 | 286,661 | 103,738 | 352,485,593 |

**Fees.** The fee paid is the transaction builder's: it is a few thousand lovelace above the formula
`44 × size + 155,381 + ⌈0.0577 × mem + 0.0000721 × steps⌉` applied to the recorded wire size. The
cause of the margin was not investigated. The node checks size one octet smaller than the wire
encoding (below).

**Tampered transactions.** In each flow, a tampered transaction was submitted first and the node
rejected it with a script failure:
- scalar opening: wrong blinding;
- running total: wrong successor commitment;
- byte opening: one flipped payload octet.

The running total's final on-chain datum equalled the off-chain `commitScalar(1150, r)`.

### Node parity of strict decoding (I10) and of the bases (I1)

Each encoding was submitted with a fixed budget, so the node evaluated the script. Every verdict
agreed four ways: the spec, the Java strict decoder, the Julc VM and the node.

| Encoding | Verdict |
|---|---|
| Identity `c0‖0^47`, `G`, `−G` | accepted, re-encoded exactly |
| `e0‖0^47`, `c0‖0^46‖01`, compression flag clear, `x = P_381` | rejected by `uncompress` (bad encoding) |
| `80‖0^47`, `a0‖0^47` (order 3) | rejected by `uncompress` (not in the group) |
| `x = 1` | rejected by `uncompress` (not on the curve) |
| `x = 4`, `G + (0, 2)` | rejected by `uncompress` (not in the subgroup) |
| 47 and 49 octets | rejected by the library's length guard, before `uncompress` |

- **Bases (I1):** `hashToGroup("G"/"H", DST_B)` equals the pinned bases on the node. A one-bit
  change to the DST is rejected.
- **What the library does not rely on:** these rejections by `uncompress` record builtin
  behaviour. The library relies only on CIP-0381's subgroup contract, plus its own length and
  round-trip guards.

### Builtin evidence (Julc VM and DevKit node; recorded, not relied on)

- **`bls12_381_G1_scalarMul`:** reduces integers up to 2^256 in magnitude mod `q`, including
  negative ones. An integer near 2^4096 fails the script. The library never passes such a scalar:
  check 1 and the delta bound run first, as exact builtin counts from a marked cost model show.
- **`bls12_381_G1_multiScalarMul`:** empty lists give the identity, and unequal lists are truncated
  to the shorter one. The library uses no MSM.
- **Node parity:** all 13 cases (seven scalars, six list shapes) gave the same verdict on the
  DevKit node as in the Julc VM, on the same transaction; the 2^4096 cases fail as script
  failures on both, not as budget or ledger rejections.

### Largest byte-opening payload

`G1BytesOpeningValidator` (1,383-octet script), with the payload in the redeemer and one fixed
public blinding `r = q − 1` (a 37-octet Plutus integer, the largest form), so the limit is the
conservative one for any blinding. The largest `n` was found by binary search with a real lock and
spend at each step, in a minimal transaction:
- the locked input;
- one pinned collateral input;
- one output;
- one key witness;
- in reference mode, one reference input.

The transaction size grew strictly with `n` at every probed point.

| Script | Largest payload | Tx size (wire / ledger) | Fee paid | Memory | Steps | `n + 1` |
|---|---:|---:|---:|---:|---:|---|
| Inline | **14,085 octets** | 16,385 / 16,384 | 915,585 | 112,353 | 393,024,337 | rejected, `MaxTxSizeUTxO` (supplied 16,385 > 16,384) |
| Reference script | **15,394 octets** | 16,385 / 16,384 | 936,731 | 113,173 | 396,882,929 | rejected, `MaxTxSizeUTxO` |

- **What binds:** at the limit, execution uses about 4% of the step limit and 0.7% of the memory
  limit; transaction size is the binding limit.
- **Transaction shape:** each extra input, output or signer lowers the limit by roughly 36–100
  octets. A real application should budget well below these figures.
- **Size accounting:** the node's size ("supplied") was the wire encoding minus one octet in every
  rejection; the ledger's measure, not the wire size, is what the limit applies to.
- **Larger documents:** a byte opening of a larger payload can be verified only off-chain.
