# SHA-2 Groth16 development proof fixtures

These retained fixtures precede the PR #112 optimizations (`9d56105`). They remain
valid with their own keys and preserve the original validation evidence. Fresh
optimized proofs and the baseline/candidate comparison are recorded separately in
[`sha2-optimization`](../sha2-optimization/README.md); never reuse these old keys
with a newly compiled optimized circuit.

These are public, 32-byte ascending-message fixtures generated by
`Sha2Groth16Test` under [ADR-0063](../../docs/adr/0063-sha256-gadget-and-sha2-assurance.md).
They use the upstream `Sha256` / `Sha512` gadgets, BLS12-381 and the pure-Java prover.
The complete digests are public as two/four consecutive big-endian 128-bit limbs.

**The setup is insecure single-party development setup.** These verification keys
are not production parameters. No proving key or toxic setup material is retained.
Groth16 remains classical and setup-dependent; these fixtures are not post-quantum.

Each case retains the fourth freshly blinded proof from its measurement run, its
verification key, public inputs, the known message and digest, and the measurement
record. The negative fixtures change each public limb separately or negate proof
point A while preserving canonical on-curve subgroup encoding. They exercise the
verification equation rather than relying solely on malformed encoding rejection.

Reproduce the ten independent checks without setup or proof generation:

```sh
# Reuse the optional harness's pinned snarkjs 0.7.6 installation.
bash assurance/sha2-circom/bootstrap.sh
python3 assurance/sha2-proof-vectors/verify.py
```

The runner requires two valid proofs to pass and six changed-limb inputs plus two
negated-A proofs to fail. It checks the verifier's expected exit code and text;
an unrelated process failure is not counted as successful rejection. Its output
and individual logs go under ignored `build/`. The committed `verification-result.json`
records the original run and exact artifact/tool hashes. All messages are deliberately
public fixtures, not secret data.

To regenerate fresh development keys, four proofs per case and timing records:

```sh
./gradlew :zeroj-integration-tests:heavyTest --tests '*Sha2Groth16Test' --max-workers=2
```

Fresh outputs go under `zeroj-integration-tests/build/sha2-proof-assurance/`; they do
not overwrite these retained vectors. Setup/proof randomness means their hashes
will differ. Timings are shared-host diagnostics with one first proof and three
subsequent samples, not a portable performance threshold. See the
[AI-assisted source review and measured results](../../docs/reviews/sha2-proof-review-issue-111.md).
