# W4–W5 implementation review — 2026-10-30

This is an implementation self-review and test record, not an independent cryptographic audit.
The underlying accepted designs remain ADR-0052/0053/0055/0057 and the normative profile specs.

## W4: imported-key Groth16

The shipped prover image has a named cubic tutorial relation and a Java `CompiledCircuit`
extension point. Its x witness is private, y is public, and every row is checked before proving.
The image contains no trusted setup. The supplied key's SHA-256 and exact circuit fingerprint
must come from the application; sending a key and its self-declared hash is not authentication.

Review corrections and checks:

- Reused `ZkeyImporterBLS381`, rather than implementing another key parser. Added a tightening-only
  `Limits` overload: bytes, wires, FFT domain and coefficients are bounded before their dependent
  allocations. A small file claiming a 2^24 domain is rejected before allocating its row maps.
- Retained the importer's canonical field, subgroup and section checks. A/B rows must match the
  compiled relation and snarkjs public-binding rows. C may be omitted in the zkey. The original
  compiled A·B=C relation is still checked against the witness before proving.
- Canonical proof/VK JSON, explicit `groth16`/`bls12381`, <=64 public inputs and existing strict
  Java point verification. Public input order is unchanged.
- Fresh proof blinders use the guarded default RNG. Two proofs for the same witness differ.
  Proofs are self-verified against the application-selected VK before export.
- ZeroJ Wasm → snarkjs verification and snarkjs → ZeroJ Wasm verification both passed using a
  newly generated, snarkjs-verified development ceremony key. Wrong key hashes/fingerprints,
  changed public inputs, non-affine points, wrong curves, disabled secrets and released handles
  are rejected. This is a real Groth16 proof of a small tutorial relation, not a large-circuit claim.
- The worker now reads bounded Node files and receives startup rejection through an explicit
  launcher hook, avoiding unhandled startup exception logging. Launcher edits are version-checked.

## W5: confidential APIs

- Java retains `VerifiedKeyShare`, `ElGamalKeyContext`, admitted `ElGamalCiphertext` and
  `VerifiedDecryptionShare`. No `verified: true`, decoded raw ciphertext, or caller-supplied bound
  is upgraded into a verified object. Handles cannot move across physical images or runtimes.
- Imported possession, encryption and decryption-share proofs use existing Groth16 verification.
  Public inputs are derived from the Java statement. The application registers a trusted VK for
  the exact six-input relation; encryption width is pinned in that registration. A VK's semantics
  cannot be established from its points alone: this remains an application/ceremony trust boundary.
- Positive import/admission/share fixtures use the existing circuit gadgets and development-only
  JVM setup, outside consumer images. All three proofs independently verify with snarkjs. Changed
  key/context/ciphertext/width and sender-selected public-input fields are rejected.
- n-of-n tally negatives cover missing/duplicate/foreign shares, mixed contexts, plaintext width,
  duplicate trustees and insufficient search limits. Search is explicitly capped at 1,000,000.
- Threshold uses all seven existing participant rounds. Authenticated sender, private/broadcast
  channel, session and round rules are delegated to the existing Java state machine. Browser
  participant count is capped at 16. Unique accepted messages are capped at 1,024 per round;
  resource overflow permanently invalidates that participant, and duplicate delivery is bounded.
  This prevents unbounded retained transcript growth through the JSON API.
- A local 2-of-3 DKG/tally and state/channel/session rejection tests pass. This is not a deployed
  distributed protocol. External authenticated-context admission, durable participant restart and
  network transport are not exposed. An application cannot reconstruct an admitted context just
  by recomputing a public transcript.
- Notes retain viewing keys and private openings. Release destroys a viewing key's mutable bytes;
  immutable copies cannot be promised erased. Ordinary scanning never returns an opening unless
  AEAD and commitment checks pass. Platform errors reject the Promise instead of returning null.
- All 53 independent note-opening accept/reject vectors pass through the Node SDK, along with
  reference reader-key checks, generated owner/auditor delivery, fresh ephemerals, altered-tag
  rejection, duplicate-reader rejection and released-key rejection.

## Remaining release gates

Browser/Node secret paths remain unassessed for side channels; no production/PQ upgrade follows
from these tests. Private witness code uses existing variable-time paths where the Java profile
allows them. Host/origin trust, trusted setup, authenticated registries, DKG transport/closure,
spending/nullifiers/state policy and compiler/runtime redistribution remain explicit obligations.
See `DISTRIBUTION.md`. No npm publication has occurred.
