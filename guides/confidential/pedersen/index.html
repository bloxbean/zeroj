Pedersen commitments

View Markdown ↗

A Pedersen commitment is a sealed envelope for a number. You publish the envelope, a 32-byte curve point, and keep the number and a random blinding value to yourself. Later you can open it to someone you choose, or prove facts about the number while it stays sealed: “at least 500”, “these inputs equal these outputs”, “this total is covered by our reserves”.

ZeroJ implements commitments on the Jubjub curve, whose arithmetic is cheap inside BLS12-381 circuits, so a Groth16 proof about a committed value costs a few thousand constraints. The profile is pedersen-jubjub-v1, designed in ADR-0051.

New to commitments? Read Commitments & encryption, explained first. Not sure a commitment is what you need? Choose how to disclose compares it with BBS, predicates, encrypted deliveries and threshold decryption.

“Offline/isolated only” restricts where you run the secret-handling code: on the user’s device or in a separate process, never in a service an attacker can time. It doesn’t weaken the commitment’s hiding or binding.

1. Commit and open

Section titled “1. Commit and open”

The commitment bytes change on every run because the blinding is random. That’s the point: committing to 1,000 twice gives two unrelated envelopes.

Decode received commitments with PedersenCommitment.decode

JubjubPoint.fromBytes only checks that the bytes are a point on the curve. It does not check the prime-order subgroup that commitments live in. Use PedersenCommitment.decode for any commitment you receive.

2. Add commitments

Section titled “2. Add commitments”

Anyone can add two commitments: C(30, r1) + C(12, r2) = C(42, r1 + r2). There’s no PedersenCommitment.add; you add the points with JubjubPoint.add.

The second line is the most important thing on this page. Commitment arithmetic wraps around at a 252-bit number l. A huge “value” plus 1 can look like 0, so a cheat could hide a negative amount inside a sum. A sum of commitments proves nothing about real-world totals unless every value is range-bounded. That’s what the circuit gadgets below do for you.

3. Prove a fact without opening

Section titled “3. Prove a fact without opening”

The program below commits to 1,000, proves “at least 500”, and plays the verifier. It uses a development-only setup, as the quickstart does, so run it with -Dzeroj.allowInsecureTrustedSetup=true.

The circuit has 2,671 constraints. Two details carry the security:

  • The verifier rebuilds the public inputs from the commitment it already holds and the threshold it requires. Comparing them with the proof’s public inputs is what stops a prover from submitting a valid proof about a different commitment or a lower threshold.
  • The blinding is declared @Secret @UInt(bits = 252). ZeroJ refuses to build a circuit whose blinding is narrower, public or a constant: CommittedThresholdCircuit.build() throws IllegalArgumentException. A 16-bit blinding could be brute-forced, which would reveal the value. The guard can’t tell whether your blinding is random, though, so always use randomBlinding(new SecureRandom()).

5. Commit to several values at once

Section titled “5. Commit to several values at once”

A vector commitment seals up to 16 values in one point, for example a credit profile of income, score, birth year and country. A proof can then check a rule over some fields and keep all of them hidden:

Vector commitments need two extra checks that single commitments don’t:

  • The point doesn’t record its layout. C([a], r) equals C([a, 0], r), so every proof binds a public schema digest with bindSchema, and the verifier checks it against a trusted PedersenSchemaRegistry.
  • A commitment proves nothing about who issued it. Accept a received commitment only with an authenticated issuance record, and fail closed without one.

The full worked example is AnnotatedVectorCommitment in zeroj-integration-tests, and the credit gate shows it on Cardano.

Commitments you didn’t make

Section titled “Commitments you didn’t make”

If your circuit receives a commitment whose opening it doesn’t know, for example another party’s balance, there are three ways in. Pick by who checks the point:

SituationAPIWho checks the point
The circuit knows the openingZkPedersenCommitment.commit(zk, value, blinding) + assertAffineEqualsThe circuit recomputes it
The opening is unknown, the point is a witnessZkPedersenCommitment.witnessInSubgroup(zk, u, v)The circuit (about 5,500 extra constraints)
The opening is unknown, the point is publicZkPedersenCommitment.fromVerifierCheckedPublic(zk, u, v)Your verifier must PedersenCommitment.decode it first

On Cardano, a validator can’t run the Jubjub subgroup check, so on-chain consumers use the first two rows.

Rules to follow

Section titled “Rules to follow”
  • Fresh random blinding, every time. PedersenCommitment.randomBlinding(new SecureRandom()); never reuse one, never derive it from public data.
  • Commit offline. commit and randomBlinding use variable-time arithmetic on secrets. Run them on the user’s device or in an isolated process.
  • Decode with PedersenCommitment.decode, never JubjubPoint.fromBytes, for received bytes.
  • Range-bound every value that means a number. Commitments bind values modulo l: commit(v, r) equals commit(v + l, r). Integer meaning comes only from declared widths and assertBalanced. Off-circuit point sums carry no such check.
  • Rebuild public inputs on the verifier side. A commitment is two public inputs, u then v.
  • The identity point is a valid commitment (to 0 with blinding 0). Check isIdentity() if your application must exclude it.
  • A proof is not a permission. Replay protection, nullifiers and binding to the spending transaction are still your job. See Application security.
