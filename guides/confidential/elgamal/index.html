ElGamal encryption

View Markdown ↗

A Pedersen commitment can only be opened by someone who knows its opening. Encryption solves a different problem: a value that a named party, such as an auditor, an auctioneer or a group of election trustees, must be able to read later without the sender’s help.

Think of a lockbox with a slot. Anyone can drop a value in using the public key; only the holder of the secret key can open it. ZeroJ uses exponential ElGamal on the Jubjub curve, which adds one more property: ciphertexts under the same key add up. A ledger can keep an encrypted running total, and the key holder decrypts only the total.

The trade-off is that decryption ends in a search, so it only works for small numbers: votes, counters, or a large amount split into 32-bit pieces called limbs. The profile is elgamal-jubjub-v1, designed in ADR-0052.

1. Encrypt, add, decrypt

Section titled “1. Encrypt, add, decrypt”

What to notice:

  • Every encryption carries a width. encrypt(key, 1200, 16, random) promises that the message fits in 16 bits. The ciphertext remembers the largest value it can hold, its bound (65,535 here), and adding two ciphertexts adds their bounds.
  • Decryption is a search over [0, bound]. JubjubDiscreteLog.forBound(...) builds a lookup table once; reuse it for many decryptions.
  • The safe API refuses mistakes instead of returning a wrong answer: a search limit below the bound, ciphertexts under different keys, a message that doesn’t fit its width.
  • Bytes carry no key and no bound. RawElGamalCiphertext.decode gives you a raw ciphertext, which has no decrypt method. Section 3 shows how it gets back in.

2. Encrypt to someone else’s key

Section titled “2. Encrypt to someone else’s key”

In example 1 one process owns the key, so NOfNKeyContext.singleKey(secretKey) is fine. A real sender only has the recipient’s published key, and must check a possession proof before using it: a zero-knowledge proof (a DLEQ proof) that whoever published the key knows its secret.

Why bother? Without it, an attacker can publish a “rogue” key crafted from other people’s keys, so that a combined key ends up decryptable by the attacker alone. ZeroJ makes the check part of the type system: the only way from bytes to a usable key goes through VerifiedKeyShare.verify, which hands your verifier the exact statement to check.

verifyDleqProof stands for your own Groth16 verification of the possession proof, over a DLEQ circuit built with ZkElGamal.assertDiscreteLogEquality. The full proven flow (possession proofs, joint key, proved ballots, proved decryption shares, tally) is the endToEnd test in AnnotatedElGamalTest.

A verifier that returns true disables the check

Every ...Verifier lambda is a promise that you checked a proof. s -> true compiles, runs and silently turns off the protection.

3. Receive ciphertexts: admit them with a proof

Section titled “3. Receive ciphertexts: admit them with a proof”

A ciphertext you receive could encrypt anything: a negative number, a huge number, a value under the wrong key. Adding it to your total would corrupt the total. So received bytes start as a RawElGamalCiphertext, and become a usable ElGamalCiphertext only through ElGamal.admit:

The statement’s public inputs are exactly PK.u, PK.v, A.u, A.v, B.u, B.v: the key and the ciphertext’s two points. Your proof must be over those values and that width, for example a circuit that calls ZkElGamal.encrypt and assertAffineEquals, as in example 4.

When is s -> true acceptable? Only when something else already verified a proof for that exact statement, for example a Cardano validator that refused the transaction unless the proof verified. The confidential points auditor does this for ciphertexts it reads from validated ledger outputs, and says so in a comment.

4. Prove what a ciphertext contains

Section titled “4. Prove what a ciphertext contains”

The most useful pattern combines a commitment and a ciphertext: “this ciphertext, encrypted to the auditor, holds the same amount as this commitment”. Then the auditor’s copy can’t be faked, even by the sender. This circuit is a minimal illustration of that idea for one 32-bit amount; it is not the reference circuit ZeroJ measured on-chain.

The program commits to 250, encrypts 250 to the auditor, proves the circuit, lets the auditor admit and decrypt the ciphertext, then plays a cheating sender who encrypts 1 instead. Run it with -Dzeroj.allowInsecureTrustedSetup=true (development setup):

The cheating sender can’t even produce a witness: no secret amount makes both the commitment and the ciphertext check out. The circuit has 8,893 constraints. Production applications split a 64-bit amount into two 32-bit limbs and encrypt each, so the auditor can decrypt it; the confidential payroll and confidential points demos do exactly that, inside their transfer and issue proofs.

Bounds and decryption cost

Section titled “Bounds and decryption cost”

Decryption recovers m·G and then searches for m. How far it can search decides what you can encrypt:

  • Widths are 1 to 64 bits, and a message must satisfy 0 ≤ m < 2^width.
  • Bounds add up. A sum of 1,000 ciphertexts of width 16 has a bound of about 65 million, even if the real total is small. Use the narrowest width that fits.
  • maxPlaintext must be at least the bound, not just the value you expect, or decrypt refuses. If no value in range matches, it throws ElGamalDecryptionException instead of guessing.
  • The default table reaches about 2⁴³. A width-64 ciphertext can be admitted and added, but not decrypted. Split amounts into 32-bit limbs.

Rules to follow

Section titled “Rules to follow”
  • Verify every key you didn’t make with VerifiedKeyShare.verify and a real possession-proof check.
  • Admit every ciphertext you didn’t make with ElGamal.admit and a real encryption-proof check, for exactly that key and width.
  • Verify every decryption share you didn’t make with VerifiedDecryptionShare.verify and a DLEQ proof. An unchecked share lets a key holder choose the result.
  • Keep widths small and decrypt only bounded values.
  • Run secret operations offline or isolated. Encrypting, decryption shares and decrypting handle secrets with variable-time code.
  • The key holder can read everything encrypted to them. If that’s too much trust in one party, split the key: see Threshold decryption.
  • Fixed randomness is test-only. Never pass your own encryption randomness; the API draws it from SecureRandom.
  • A proof is not a permission. Binding ciphertexts to transactions, replay and authorization are application rules. See Application security.
