Threshold decryption

View Markdown ↗

With ElGamal encryption, whoever holds the secret key can read every ciphertext. For an election, a sealed-bid market or a shared treasury, that’s too much trust in one party. Threshold decryption splits the key among n trustees so that:

  • any t + 1 of them can decrypt together;
  • any t or fewer learn nothing, even if they collude;
  • the full secret key never exists anywhere, not even during setup.

The trustees create the key together with a distributed key generation (DKG): each trustee deals secret shares to the others and publishes commitments that let everyone check the shares, so a cheating dealer is caught and excluded. Afterwards each trustee holds one share, and everyone knows the joint public key that voters encrypt to.

ZeroJ implements the New-DKG protocol of Gennaro, Jarecki, Krawczyk and Rabin (J. Cryptology 2007) as the profile elgamal-jubjub-threshold-v1 (ADR-0053). The private shares can travel over a public board, encrypted with HPKE (RFC 9180), following dkg-share-delivery-hpke-v1 (ADR-0054).

Choose t and n

Section titled “Choose t and n”

t is the number of corrupted trustees the scheme tolerates, not the number needed to decrypt. Decrypting needs t + 1. The protocol requires an honest majority, 2t + 1 ≤ n, and supports up to 64 trustees.

DkgConfig.create(t, n, …)Decrypting needsTolerates
create(1, 3, …)any 2 of 31 corrupted trustee
create(2, 5, …)any 3 of 52
create(3, 7, …)any 4 of 73

A 4-of-5 policy isn’t possible: it would need t = 3 with n = 5, which breaks the honest majority. And remember the other side of the threshold: any t + 1 trustees who collude can decrypt any single ciphertext, not just the total.

1. Run the key generation and decrypt a tally

Section titled “1. Run the key generation and decrypt a tally”

This program runs a 2-of-3 key generation in one process, encrypts five 0/1 votes to the joint key, adds them, and has two trustees decrypt only the total. In a real deployment each trustee is a separate, isolated machine, and the messages travel over your own channels.

The key generation is seven rounds. In each round every trustee processes what it received and sends its next messages. closeRound() is the round deadline: whatever didn’t arrive in time counts as missing, which is how a silent trustee gets excluded instead of blocking everyone. Two rules of the in-memory loop matter in real code too:

  • Every trustee also receives its own broadcasts, and SHARE messages go only to their one recipient, through receivePrivate.
  • An abort is final. Start a new attempt with a new attempt number in DkgConfig.create; never reuse one.

2. Deliver private shares over a public board (HPKE)

Section titled “2. Deliver private shares over a public board (HPKE)”

Each trustee’s SHARE messages are secrets meant for one recipient. If you don’t have private channels between trustees, ZeroJ can encrypt them with HPKE (RFC 9180, Base mode, with X25519, HKDF-SHA256 and ChaCha20-Poly1305) and post the encrypted envelopes on the same public board as everything else. The order of posts is part of the security, so the API enforces round barriers:

  1. Round 0: announce. Each trustee generates fresh delivery keys for this attempt and posts the announcement (106 bytes). Once the round-0 window is final, every trustee builds the same DkgKeyDirectory from it.
  2. Round 1: envelopes first. DkgShareDelivery.start replaces start(). Post the envelopes (223 bytes each, n(n−1) per attempt), and post the COMMITMENTS broadcasts only after the envelopes are final, or atomically with them.
  3. Close round 1 only through closeRound1, passing the round-1 window after its cutoff and after it’s final on the board. Plain closeRound() refuses round 1. The delivery keys are destroyed here.
  4. Rounds 2 to 7 are plain broadcasts, as in example 1.

This program runs the same 2-of-3 key generation as example 1, with every message on one board. Posts are signed with each trustee’s Ed25519 roster key, and the board doubles as the verifier the API asks for. Its last step, letting an outsider admit the key, is in section 3.

Two rules for your own board verifier: authenticate and roundClosed must return false, never throw, on bad input; and roundClosed must only say true for the agreed, complete record of that round. A roundClosed that always returns true defeats the protection.

HPKE here has no forward secrecy and isn’t post-quantum: a delivery key that leaks before it is destroyed exposes that trustee’s shares.

Operating rules

Section titled “Operating rules”

The library enforces the protocol; it can’t enforce how you run it. A deployment must:

  • Isolate trustees. Each one runs on its own machine, under its own control.
  • Fix the configuration in advance. t, n, the roster and the application context come from a trusted source, such as a published election manifest, never from the network mid-run.
  • Never reuse an attempt number for the same context.
  • Deliver private shares on time. A missed share triggers a complaint, and answering a complaint publishes that share. Timely private delivery is a precondition for secrecy.
  • Decrypt once. Decrypt only the final total, after the deadline. Decrypting running totals and subtracting them reveals individual votes.
  • Verify every decryption share you receive with VerifiedDecryptionShare.verify and a DLEQ proof. In example 1 the shares are “verified by construction” because one process made them; a separate tallier gets them as bytes.
