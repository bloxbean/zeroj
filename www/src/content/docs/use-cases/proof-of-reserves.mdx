When an exchange or custodian fails, customers find out too late that the money wasn't there. The
usual remedies are weak. An auditor's report asks you to trust the auditor. Publishing every
account balance destroys customer privacy. A plain Merkle proof lets you see your neighbours'
balances. Stablecoin issuers, bridges, lending protocols and DAO treasuries face the same question:
*can you prove you're solvent without opening your books?*

<ReservesWalkthrough />

## The zero-knowledge idea

**The custodian proves "the balances committed in this published liabilities root are all
non-negative, add up to exactly this total, and that total is covered by our reserves", without
revealing any balance.**

Each customer account becomes a leaf in a Merkle tree, and the root is published. The circuit
rebuilds the whole tree from the private balances, so the root commits to exactly the numbers being
summed. The custodian can't sum one set of balances and publish another. Every balance is a 64-bit
unsigned integer, and range checks rule out a negative "balance" that would quietly shrink the
total.

Customers close the loop. Each gets the Merkle path for their own leaf, recomputes the root, and
compares it with the attestation on the chain. If the custodian left someone out or understated a
balance, that customer can tell.

:::caution[Reserves are claimed, not proven]
In this design `totalReserves` is a public input the custodian supplies. The circuit proves
liabilities ≤ that number. It does not prove the custodian controls the funds. On Cardano you can
check reserves held at known addresses directly; off-chain reserves need an attestation or oracle
you trust.
:::

### Why the leaves are salted

A customer's Merkle path contains other customers' leaves: the sibling next to their own leaf is a
neighbour's. If a leaf were just `Poseidon(accountId, balance)`, a customer who can guess the
neighbour's id could hash every plausible balance until one matched the sibling, and so learn the
neighbour's balance. The demo's leaves used to work that way.

Now every account gets a fresh 252-bit salt in every snapshot, and the leaf is

```text
leaf = Poseidon(Poseidon(idTag, salt), balance)
```

where `idTag` is a fixed Poseidon encoding of the account id. A neighbour who doesn't know the
salt has nothing small left to guess. Unused slots get a random id and balance 0, so they look like any other leaf.

## What stays private, what's public

| Input | Visibility | Why |
|---|---|---|
| `accountIds` | Secret | Each is the salted id `Poseidon(idTag, salt)`, so identities stay private and leaves can't be guessed |
| `balances` | Secret | Individual balances; each is range-checked to 64 bits |
| `totalReserves` | Public | The custodian's claimed reserves, which must be checked independently |
| `liabilitiesRoot` | Public | Commits to every leaf; customers check their inclusion against it |
| `totalLiabilities` | Public | The exact sum of all balances |
| `isSolvent` | Public | Proven equal to `totalReserves ≥ totalLiabilities`; the minting policy fixes it to 1 |

## How it works

1. **Snapshot.** The custodian takes the customer balances at a point in time, draws a fresh salt
   for every account and builds the Poseidon Merkle tree.
2. **Prove.** It generates a Groth16 proof over the private balances with the four public inputs
   above.
3. **Attest on-chain.** It mints this period's attestation token into an output at the attestation
   script's address. The minting policy verifies the proof against the values in that output's
   datum, so an insolvent claim can't mint.
4. **Customers verify.** Each customer receives their salt, balance and Merkle path, recomputes the
   root in their browser, reads the attestation from the chain, and compares the two.
5. **Repeat.** Each period gets new salts, a new proof and its own token.

```text
custodian (private)                        public
───────────────────                        ──────
16 × (salted id, balance)  ─prove─▶  mint token I2OSP8(p), locked at the script address
(8 accounts + 8 random padding)
                                     datum: Attestation(p, liabilitiesRoot, totalLiabilities, totalReserves)
                                     redeemer: Groth16 proof, checked against the datum with isSolvent = 1
customer: salt + leaf + path ──────▶ root from the chain indexer = my root? ✓
```

:::tip[Hide the total too]
This design publishes `totalLiabilities`. If the total is sensitive as well,
[Proof of solvency with hidden balances](/use-cases/private-solvency/) commits to each balance with
a Pedersen commitment, proves the hidden total fits under reserves locked for an attestation period,
and lets each customer open their own entry from an encrypted on-chain delivery. An auditor opens
only the total.
:::

## The circuit

This is simplified from the demo's `SolvencyProof`: constructor validation is trimmed, and the demo
requires `numLeaves == 1 << treeDepth`. Salting didn't change the circuit. Its `accountIds` witness
now holds the salted ids, so the existing keys still work.

```java title="SolvencyProof.java"
import org.zeroj.circuit.annotation.*;
import org.zeroj.circuit.lib.poseidon.PoseidonParams;
import org.zeroj.circuit.lib.poseidon.PoseidonParamsBLS12_381T3;
import org.zeroj.circuit.lib.zk.ZkPoseidon;

@ZKCircuit(name = "solvency-proof",
           nameTemplate = "solvency-proof-d{treeDepth}-n{numLeaves}-bls-poseidon", version = 1)
public class SolvencyProof {
    private static final PoseidonParams POSEIDON = PoseidonParamsBLS12_381T3.INSTANCE;
    private final int treeDepth;
    private final int numLeaves;

    public SolvencyProof(@CircuitParam("treeDepth") int treeDepth,
                         @CircuitParam("numLeaves") int numLeaves) {
        this.treeDepth = treeDepth;
        this.numLeaves = numLeaves;
    }

    @Prove
    ZkBool prove(ZkContext zk,
                 @Public @UInt(bits = 64) ZkUInt totalReserves,
                 @Public ZkField liabilitiesRoot,
                 @Public @UInt(bits = 64) ZkUInt totalLiabilities,
                 @Public ZkBool isSolvent,
                 @Secret @FixedSize(param = "numLeaves") ZkArray<ZkField> accountIds,
                 @Secret @UInt(bits = 64) @FixedSize(param = "numLeaves") ZkArray<ZkUInt> balances) {

        // Leaves and running sum over the private balances
        ZkUInt sum = balances.get(0);
        ZkField[] level = new ZkField[numLeaves];
        for (int i = 0; i < numLeaves; i++) {
            level[i] = ZkPoseidon.hash(zk, POSEIDON, accountIds.get(i), balances.get(i).asField());
            if (i > 0) sum = sum.add(balances.get(i));
        }

        // Rebuild the Merkle root from the same leaves
        for (int d = 0; d < treeDepth; d++) {
            ZkField[] next = new ZkField[level.length / 2];
            for (int i = 0; i < next.length; i++) {
                next[i] = ZkPoseidon.hash(zk, POSEIDON, level[2 * i], level[2 * i + 1]);
            }
            level = next;
        }

        return level[0].isEqual(liabilitiesRoot)
                .and(sum.asField().isEqual(totalLiabilities.asField()))
                .and(isSolvent.isEqual(totalReserves.gte(totalLiabilities)));
    }
}
```

The circuit covers a fixed batch. The demo defaults to depth 4, which is 16 accounts. A real book
of accounts needs a much larger circuit or a batching scheme, and proving cost grows with it. See
[Performance](/guides/proving/performance/).

## On Cardano

An attestation is a **minted, locked token**. The demo's `ReserveAttestation` is one JuLC
multi-validator that is both the attestation's minting policy and its script address. Its
parameters are the custodian's key hash, the period clock (`genesisMs`, `periodMs`) and the
verification key. Period `p` covers `[genesisMs + p·periodMs, genesisMs + (p+1)·periodMs)`; the demo
uses five-minute periods.

- **Mint (attest).** The custodian signs. The mint is exactly one token named `I2OSP8(p)` (the
  period as 8 bytes), sent to the single output at the script's own enterprise address (payment
  credential, no stake credential). That output holds only ADA and the token, carries no reference
  script, and has the inline datum
  `Attestation(period, liabilitiesRoot, totalLiabilities, totalReserves)`. The redeemer is the
  proof, which must verify against `[totalReserves, liabilitiesRoot, totalLiabilities, 1]` read from
  that datum. An honest proof of insolvency has `isSolvent = 0`, so it can't mint.
- **Spend (release).** The only spend is a custodian-signed burn of that token, after the period has
  ended. The datum can't change while the token exists.

Why a token? The demo used to lock a plain UTxO with the four public inputs in its datum and check
the proof only when someone spent it. Anyone can create a UTxO with any datum, so a datum alone
proved nothing. Now readers look only for the token, and the token can't exist without a proof over
its own datum.

**One per period.** The script doesn't stop the custodian minting a second token for the same
period, but every mint is visible. The demo's custodian service refuses a second attestation for a
period itself (HTTP 409), and the customer check reads the token's whole mint history from the
chain indexer and refuses a period unless it shows exactly one mint and no burn. Without that check,
a custodian could split its liabilities across several trees against the same reserves.

The mint also doesn't check the transaction's validity range. Only the burn checks time. So a
custodian can mint a future period's token in advance, from today's tree. The customer check looks
only at the current period, so when that period arrives it is checked against the old tree.

**Checking against the chain, not the custodian.** The customer page gets its salt, balance, leaf
index and path from the custodian, and recomputes the root in the browser. It then finds the current
period's token under the known policy id through the chain indexer (Yaci Store), not through the
custodian's API, and compares the attested root with its own. The customer also compares the
balance with their own records.

A valid proof is still not the whole story. The proof checks the sum of the balances the custodian
put in the tree. It doesn't check that those balances are true, or that the reserves exist. See
[Application security](/guides/verifying/application-security/).

## Security considerations

- **Reserves are custodian-declared.** `totalReserves` is whatever the custodian puts in the datum;
  the demo doesn't check it against on-chain holdings. Check holdings directly, or rely on an
  attestation you trust. Watch for reserves borrowed just for the snapshot. Proving over several
  periods, or at unpredictable times, makes that harder.
- **The proof checks the sum, not the balances.** The custodian chooses the balances in the tree.
  Omissions and understated balances are only caught by customers who check. Make checking easy.
- **The proof isn't bound to its period.** The period is in the token name and datum, not in the
  proof's public inputs, and the mint doesn't check the validity range. A custodian could re-attest
  an old solvent tree (the same root, liabilities and reserves) for a new period, or mint a future
  period's token in advance. Customers would then see old balances, so comparing the balance
  with their own records is what catches it. A real design puts the period in the public inputs.
- **Trust the indexer and the page.** The customer trusts the indexer they point the page at. In the
  demo the custodian serves the customer page, and the policy id and clock it pins on first load come
  from the custodian. A real customer takes them from a published, independent source and runs the
  check from code they trust, such as a wallet or a third-party page.
- **Operator view.** The demo server is the custodian. It holds every balance, every salt and the
  custodian key, and its `/accounts` and `/verify/{id}` endpoints answer anyone. That's the demo
  operator's view; a real custodian gives each customer only their own inclusion data, after
  authenticating. Privacy in the demo holds against chain observers, not against the demo server.
- **Trusted setup.** The demo uses a single-party development setup. Production keys come from a
  multi-party ceremony ([Trusted setup, explained](/learn/trusted-setup/)).

## Try it

The demo lives in
[`proof-of-reserves`](https://github.com/bloxbean/zeroj-usecases/tree/main/proof-of-reserves). With
Yaci DevKit running (see [Run the demos](/use-cases/overview/#run-the-demos)):

```bash
./demo.sh proof-of-reserves --run
```

`--run` builds the liabilities tree over the demo accounts and proves solvency against 10,000 ADA of
declared reserves, and mints the current period's attestation token, whose minting policy verifies
the proof. In the UI you can add accounts, try a reserve figure below total liabilities to see the
attestation refused, try a second attestation in the same period (the demo server refuses it, and the customer page
would refuse the period too), and run a customer's
inclusion check against the chain. The first start generates a development setup cache and a
random custodian key, which can take a few minutes. `./demo.sh proof-of-reserves --clean-cache`
removes the key, the deployment state and the attested snapshot together.
