Private voting

View Markdown ↗

DAOs, community treasuries and project councils increasingly vote on-chain, and on a public ledger every ballot is tied to an address. That invites vote buying (“show me your transaction and I’ll pay you”), social pressure from peers and employers, and whales watching the count before they decide. What you want is a vote where eligibility and one-person-one-vote can be checked by anyone, but nobody can tell who voted for what, and only the final result is ever revealed.

The zero-knowledge idea

Section titled “The zero-knowledge idea”

The voter proves “I’m on the eligible-voter list, this is my one nullifier for this election, and this encrypted ballot holds a 0 or a 1”, without revealing who they are or how they voted.

Four pieces make this work:

  • Voter list. Each voter’s public key is Poseidon(secretKey, 0). The organizer puts all public keys into a Merkle tree and publishes only the root.
  • Nullifier. Poseidon(secretKey, electionId). It’s deterministic, so the same voter in the same election always produces the same value, and a second vote is caught. A different electionId gives an unrelated nullifier, so a voter’s ballots can’t be linked across elections.
  • Encrypted ballot. The vote, encrypted with exponential ElGamal to an election key that three trustees hold together. Nobody can open a single ballot, but ballots can be added up while still encrypted.
  • Tally. After voting closes, the trustees decrypt only the total, once, and prove they did it honestly.

The circuit ties the first three to one secret key. A voter who switches keys to get a fresh nullifier isn’t in the tree, and a voter who keeps their key gets the same nullifier again.

If ElGamal is new to you, Commitments & encryption, explained introduces it with an interactive lockbox.

Why not just hash the vote?

Section titled “Why not just hash the vote?”

A hash looks like a natural way to hide a vote: publish Poseidon(vote, nullifier) and nobody can undo the hash. The first version of this demo did exactly that, and it doesn’t work. The nullifier is public and a vote is only 0 or 1, so anyone can hash both choices and see which one matches. Hiding a value with a hash only works when there are far too many possible values to try. A yes/no vote, an age or a small amount can always be guessed this way.

A secret random salt stops the guessing, but then nobody can count the votes without every voter coming back to reveal their salt, which reveals their vote at the end. Encryption solves both problems at once: each ballot uses fresh randomness, so it can’t be matched by guessing, and ElGamal ciphertexts can be added, so the total can be decrypted without opening any ballot. The hash version was reported as issue #7 and replaced with the encrypted ballot described on this page (ADR-0005).

What stays private, what’s public

Section titled “What stays private, what’s public”
InputVisibilityWhy
secretKeySecretThe voter’s identity; it derives both the public key and the nullifier
Merkle path (siblings, pathBits)SecretThe path would reveal the voter’s position in the list
voteSecretInside the ciphertext; the proof limits it to 0 or 1
randomness (252 bits)SecretFresh for every ballot; it’s what makes two ballots for the same choice look unrelated
electionId, voterRootPublicThe election and its list of eligible voters, fixed in the on-chain script
Election key PK (PK.u, PK.v)PublicThe trustees’ combined key, also fixed in the script
nullifierPublicRecorded on-chain to block a second vote
Ballot (A, B) (A.u, A.v, B.u, B.v)PublicThe encrypted vote; it reveals nothing without the trustees

How it works

Section titled “How it works”
  1. Trustee keys. Each of the three trustees generates a key pair and publishes its public key with a zero-knowledge proof of possession (a DLEQ proof that it knows the matching secret). Without that proof, a dishonest trustee could choose its key to cancel the others’ and read every ballot alone. The election key is the sum of the three public keys.
  2. Register. The organizer collects each voter’s public key Poseidon(secretKey, 0), builds the Merkle tree and publishes voterRoot. The election ID, the root, the election key and the voting deadline become parameters of the on-chain scripts.
  3. Encrypt and prove. The voter encrypts their vote v with fresh randomness k: A = [k]·G, B = [v]·G + [k]·PK. A Groth16 proof, made with ZeroJ’s pure-Java prover, shows that the voter is on the list, that the nullifier is theirs, and that (A, B) encrypts a 0 or a 1 under PK. A ballot that tries to count twice (v = 2) has no valid proof. In a real deployment this runs on the voter’s own device; the demo proves server-side for convenience.
  4. Submit. A transaction mints one token whose name is the nullifier and creates a list node that holds the ballot. The minting policy verifies the proof on-chain before the deadline, and the nullifier is inserted into an on-chain sorted list.
  5. Reject repeats. A second vote from the same key has the same nullifier. The list already contains it, so the insert fails.
  6. Add up. Anyone can add the ballots: (ΣA, ΣB) is an encryption of the number of YES votes.
  7. Decryption shares. After the deadline, each trustee publishes D_j = [sk_j]·ΣA together with a DLEQ proof that it used the same secret as its registered key. A wrong share fails its proof.
  8. Count. ΣB − (D₁ + D₂ + D₃) = [YES]·G. The number of YES votes is small, so a short search recovers it. Anyone can repeat every check from chain data and the published election manifest.

The trustees decrypt the total exactly once, after the deadline. Decrypting a running total twice would let anyone subtract the two results and learn the votes cast in between.

The ballot circuit

Section titled “The ballot circuit”

Lightly simplified from the demo’s PrivateBallotProof: constructor validation is trimmed. ZkElGamal.encrypt is ZeroJ’s elgamal-jubjub-v1 encryption relation, so the demo doesn’t implement any ElGamal itself.

The @UInt(bits = 1) on vote is what limits a ballot to 0 or 1. The circuit has 9,477 constraints at tree depth 10. The annotation processor generates a PrivateBallotProofCircuit companion that you compile to R1CS and prove with Groth16. Before you trust a circuit like this, test it with invalid witnesses: a key that isn’t in the tree, a nullifier from another election, a vote of 2, a ballot encrypted to another key. It should reject every one. See Testing circuits.

On Cardano

Section titled “On Cardano”

The demo uses two Plutus V3 scripts written in Java with JuLC:

  • VoteZkMintingPolicy verifies the ballot proof with Groth16BLS12381Lib.verify(...) from zeroj-onchain-julc. The redeemer carries only the proof. Every one of the nine public inputs comes from the script’s parameters (electionId, voterRoot, the election key, and the verification key) or from the ledger: the nullifier is the name of the single token minted, and the ballot is read from the inline datum of the list node that receives it. The transaction must also be valid only up to the voting deadline.
  • VoteListValidator keeps nullifiers in a sorted linked list, one UTxO per nullifier, each holding its ballot. Inserting between two neighbours proves the new nullifier wasn’t there before. Votes that land in different parts of the list touch different UTxOs, so they don’t contend. Each node locks about 2 ADA.

A valid proof is not authorization, which is why the election’s values are script parameters and not redeemer fields: otherwise a voter could prove membership in a tree they built themselves, or encrypt to a key they hold. See On-chain verification.

Limits

Section titled “Limits”
  • Every trustee is needed, and all of them together could read any ballot. The demo’s key is n-of-n: if one trustee disappears, nothing can be decrypted, and the three together could decrypt a single ballot instead of the total. ZeroJ’s threshold ElGamal with a distributed key generation is the t-of-n alternative: any t + 1 trustees can decrypt, and fewer learn nothing. The demo doesn’t use it yet.
  • The demo server knows every vote. For convenience it holds every voter’s and trustee’s secret and proves on their behalf. In a real election each voter proves on their own device and each trustee keeps its own key.
  • Demo voter keys are random and kept. The test voters’ secret keys come from SecureRandom and are stored, owner-only, in the demo’s data directory. Earlier versions used small fixed numbers (10000 + i), so anyone could compute each voter’s nullifier, match ballots to voters, or vote for a voter who hadn’t voted yet. Voting “as Alice” by label in the demo is the operator acting for that voter, not the voter signing in.
  • Small or unanimous results reveal votes. If all three ballots are YES, everyone knows how each voter voted. The total is always public.
  • The vote list is public. Anyone can see how many ballots were cast and when.

Security considerations

Section titled “Security considerations”
  • The voter list is a trust point. Whoever builds the tree decides who can vote. Publish the leaves so members can check their inclusion and spot keys that shouldn’t be there.
  • Check the trustees’ key proofs. The election key is only as good as the possession proofs behind it; the manifest publishes every key with its proof so anyone can rebuild it.
  • Watch transaction-level metadata. In the demo a service wallet submits and pays for every vote. If voters pay fees from their own wallets, the fee input links them to their ballot. Use a relayer and be mindful of timing.
  • No receipt-freeness or coercion resistance. A voter can prove to a vote buyer how they voted by handing over the randomness k, or hand over their secret key entirely. Anti-collusion designs such as MACI address this. This demo doesn’t.
  • Key theft is vote theft. Anyone who learns a voter’s secret key can vote in their place.
  • Trusted setup. The demo uses a single-party development setup for both its circuits. A real election needs keys from a multi-party ceremony (Trusted setup, explained).
